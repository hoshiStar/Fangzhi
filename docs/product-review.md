# 方志检索项目产品评审与优化建议

> 评审日期：2026-11-11  
> 评审范围：项目结构、核心数据链路、桌面端、小程序、OCR、下载与阅读、验证工具及发布现状  
> 文档性质：产品与代码只读评审，不代表完整真机、联网或大规模数据验收

## 一、整体判断

这个项目已经不是单纯的验证脚本，而是一个具备业务闭环的桌面端 MVP：

> 夸克地方志目录采集 → 书目解析聚合 → 检索筛选 → 下载 → PDF 在线/本地阅读 → OCR 全文检索

当前最有价值、最接近正式交付的能力是：

> **Windows 桌面端的地方志书目检索、夸克下载和 PDF 在线/本地阅读。**

OCR 全文检索已经证明技术路线可行，但仍属于小样本试点；微信小程序适合作为轻量、只读的离线书目目录，不应被视为桌面版的完整平移。

从产品角度，建议近期将定位收敛为：

> **面向地方志研究者、资料收集者和相关从业者的 Windows 桌面检索与阅读工具。**

暂时不建议包装成“通用网盘搜索工具”或“全库全文数字图书馆”：当前文件名解析和目录规则高度依赖特定地方志分享库，OCR 也尚未覆盖全库。

下一阶段的重点不应是继续扩张功能，而应先把现有“检索—下载—阅读”闭环做到：

- 数据不丢失；
- 文件不串用；
- 结果可解释；
- 状态可恢复；
- 发布可复现。

## 二、项目现状与功能成熟度

### 2.1 数据规模

当前本地数据约为：

| 指标 | 当前规模 |
|---|---:|
| 物理文件 | 4600 个 |
| 聚合书目 | 3149 部 |
| 数据总量 | 约 99.9GB |
| PDF | 4404 个 |
| 其他格式 | DJVU、DOC、RAR、UVZ、TXT 等 |
| OCR 数据 | 10 个文件有文本引用，1 个文件标记完成 |

### 2.2 核心链路

```text
夸克分享目录
    ↓
目录爬取、分页、重试、断点续爬
    ↓
文件名与目录著录解析、书目聚合
    ↓
full / lean / mini 多级索引
    ↓
桌面端检索、筛选、下载、PDF 阅读、OCR 检索
    ↓
小程序离线书目查询
```

### 2.3 模块判断

| 模块 | 已有能力 | 成熟度判断 |
|---|---|---|
| `packages/core` | 目录爬取、断点续爬、文件名解析、书目聚合、检索筛选、统计 | 主体完整，数据治理仍需加强 |
| `apps/desktop` | 搜索、筛选、详情、索引更新、账号、下载、PDF 阅读 | 最接近正式交付 |
| OCR | OCR 文本阅读、书内搜索、全库正文搜索、跳页高亮 | 技术路线可行，仍属试点 |
| `apps/miniprogram` | 离线搜索、筛选、详情、复制分享链接和文件名 | 只读目录，尚需真机与发布验收 |
| 下载 | 串行队列、取消、进度、`.part`、Range 续传 | 已实现，但可靠性存在缺口 |
| 发布 | Windows x64 便携版 | 已有产物，但数据版本不同步 |
| 验证工具 | 检索、索引、爬取和 CDP 诊断脚本 | 偏开发诊断，不是完整测试体系 |

Core 和桌面端类型检查、小程序逻辑冒烟目前通过；但项目仍缺少系统化自动测试、真机验收和持续集成。

## 三、P0：应优先修复的问题

### 3.1 防止更新索引后丢失 OCR 关联

`packages/core/src/build-index.ts` 重建索引时会重置 OCR 状态，桌面端随后覆盖索引。结果可能是 OCR 文件仍然存在，但阅读器无法发现这些文本。

建议：

1. 按文件 `fid` 合并旧索引中的 `textRef`、OCR 状态和完成信息。
2. 根据实际 OCR 文件重新核对完成度。
3. 使用临时文件加原子替换写入索引，避免中断后留下半份数据。
4. 增加“更新索引后 OCR 仍可检索”的自动回归测试。
5. full、lean、mini 和便携版数据统一由同一次构建生成。

### 3.2 修复同名文件下载覆盖和错读

当前下载路径只使用文件名，没有包含书目 ID 或文件 ID。不同文件同名时，可能相互覆盖；阅读器也可能把另一份同名文件误判为当前文件的本地副本。

建议采用以下目录结构：

```text
下载目录 / 书目ID / 文件ID / 原始文件名
```

同时：

- 保存包含 `fid`、大小、完成状态和校验信息的下载清单；
- 本地优先阅读前核对文件身份，不能只看文件名；
- 为已有扁平下载目录提供兼容查找或迁移方案。

### 3.3 统一桌面端与小程序的检索语义

full 索引保留噪声标记，而 mini 索引裁剪后丢失该信息，导致两端相同查询的结果不一致。

建议：

- 在 mini 中保留噪声字段，或在导出前统一过滤；
- 建立同一查询的跨端一致性测试；
- 明确“总书目数”和“实际可检索书目数”的统计口径；
- 统一桌面端、小程序对噪声、分卷和弱匹配结果的处理。

### 3.4 收紧账号与外部链接安全边界

建议优先处理：

- Cookie 加密不可用时明确警告或拒绝持久化，不应静默明文保存；
- 外部链接仅允许 `https:`，并校验可信主机；
- 切换夸克账号时清除账号相关缓存令牌；
- 诊断脚本强制使用独立测试环境，避免修改真实 Cookie；
- 评估启用 Electron renderer sandbox 的可行性。

如果准备公开传播，还需补充内容版权、第三方分享来源、网盘服务条款、账号限速及封禁风险说明。

### 3.5 修正发布数据不同步

当前工作区已有 10 个 OCR 文件，而便携版仅带 1 个，便携目录不能代表当前源码和数据的完整状态。

建议每次发布统一生成：

- 桌面应用构建产物；
- full、lean、mini 索引；
- OCR 数据；
- 应用版本、索引版本、爬取时间、OCR 数据版本；
- 文件清单与校验和。

## 四、P1：核心产品体验优化

### 4.1 提升搜索结果的准确性与可解释性

当前“文件内容”命中实际可能只是文件名、卷次或分志命中，并非正文，容易与 OCR 全文搜索混淆。

建议将命中类型明确区分为：

- 精确匹配；
- 部分关键词匹配；
- 文件信息匹配；
- OCR 正文匹配；
- 近似匹配。

同时：

- 提供“全部关键词严格匹配”模式；
- 强结果、部分命中和近似结果分区展示；
- 区分真实命中总数与截断后保留的结果数；
- 让筛选统计对应当前完整结果集；
- 将繁简归一扩展到元数据检索；
- 为书名、地名、作者建立标准检索字段和同义词。

### 4.2 建立书目人工校正机制

目前约有 30 部低置信度书目，朝代等字段覆盖率也有提升空间。仅继续堆叠文件名解析规则，长期维护成本会越来越高。

建议增加：

- “待核对书目”列表；
- 人工修改书名、朝代、地名、作者和版本；
- 书目合并与拆分；
- 修正规则独立保存，更新索引时自动保留；
- 将“分享目录分组”和“标准省份”拆成不同字段；
- 数据质量报表，持续跟踪解析覆盖率、异常样本和人工修正率。

### 4.3 将 OCR 建设为可管理的任务中心

目前 OCR 需要用户自行安装环境并运行 Python 脚本，不适合普通用户。

建议桌面端提供：

- 待识别、进行中、部分完成、失败、完成状态；
- 指定单本、指定页范围、失败重试和后台续跑；
- OCR 模型与依赖状态检查；
- 明确显示“全文检索覆盖 X/4600 个文件”；
- 全文无结果时提示“可能尚未 OCR”，避免误导；
- 数据量扩大后，将全文扫描迁出主进程，并建立真正的全文索引；
- 即使 PDF 暂时不可在线读取，也允许直接打开已有的本地 OCR 文本。

### 4.4 完善下载与阅读连续性

建议：

- 持久化下载队列，重启后恢复未完成任务；
- 支持单文件下载、仅下载缺失文件、重试失败文件；
- 增加磁盘空间和文件完整性检查；
- 将取消信号贯穿令牌刷新、换链和下载全过程；
- 阅读器补充目录、书签、缩放、最近阅读和阅读位置记忆；
- 为链接失效、快速翻页、损坏 PDF、Range 续传等场景建立测试。

### 4.5 优化界面信息层级

建议重点调整：

1. 搜索无结果时清空或收起旧书详情，避免“中间无结果、右侧仍显示上一本书”的上下文冲突。
2. 将“更新索引、数据目录、账号”收进设置或工具菜单，突出搜索主任务。
3. 提供已选筛选条件汇总和一键清除。
4. 低置信度不要只显示数字，应说明“为什么待核对”。
5. 文件较多的书目增加卷次搜索、分组折叠和已下载标记。
6. 将索引进度、下载进度和 OCR 进度统一到明确的任务反馈体系中。

## 五、P2：工程化与后续扩展

### 5.1 建立可重复测试体系

优先补充：

- 文件名解析 fixture：年号与地名冲突、纯数字文件、多版本、分志、压缩分卷；
- full、lean、mini 跨端一致性测试；
- 爬取中断与重复文件的隔离测试；
- 同名下载、Range 续传、链接失效测试；
- PDF 本地/在线阅读及异常响应测试；
- OCR 标准样本、识别质量和检索高亮回归；
- 使用独立 Electron 用户目录的端到端测试；
- 小程序真机渲染与发布验收。

### 5.2 统一开发、数据和发布流程

建议：

- 在根目录提供统一的开发、测试、构建和发布命令；
- 持久化用户选择的数据目录；
- 明确旧用户索引与新版本内置索引的升级策略；
- 发布流程生成版本清单和校验和；
- 再逐步加入安装包、代码签名和自动更新。

### 5.3 清理文档与实验代码边界

建议：

- 增加真实 README，说明产品边界、安装、开发、数据构建、OCR、测试和发布；
- 更新已经落后于代码现状的交接文档；
- 将 `quark-probe` 明确归档为实验材料，或移出主产品源码树；
- 将验证脚本区分为“只读诊断”“会写数据”“需要真实账号”三类，避免误运行。

### 5.4 控制小程序与格式扩展边界

小程序应继续坚持“轻量离线书目查询”定位，先完成真实 AppID、开发者工具和真机验收，不急于加入下载与阅读。

DJVU、DOC 等格式支持应放在 PDF 稳定性和 OCR 覆盖之后，避免同时扩张过多战线。

## 六、推荐迭代路线

### 第一阶段：可信可用

目标是消除数据正确性、安全和发布风险：

- 保留索引更新后的 OCR 关联；
- 修复同名下载覆盖与错读；
- 统一跨端检索结果；
- 修复 Cookie 与外部链接安全边界；
- 重新生成并核验便携版。

### 第二阶段：稳定好用

目标是提升核心用户流程：

- 优化搜索解释与筛选；
- 改善界面上下文和任务反馈；
- 持久化下载队列；
- 建立书目人工校正机制；
- 补齐关键自动化测试。

### 第三阶段：形成差异化

目标是建立普通网盘无法提供的能力：

- 扩大 OCR 覆盖；
- 建设 OCR 任务中心和全文索引；
- 提升书内搜索、定位与阅读体验；
- 在核心链路稳定后，再评估更多文档格式和移动端能力。

## 七、建议关注的产品指标

后续可用以下指标判断迭代是否真正有效：

| 方向 | 建议指标 |
|---|---|
| 数据正确性 | OCR 关联保留率、同名文件串用数、跨端结果一致率 |
| 检索质量 | 首条命中率、无结果率、低置信度书目数量、人工修正率 |
| 下载可靠性 | 下载成功率、续传成功率、重启恢复率、失败原因分布 |
| 阅读体验 | 打开成功率、首屏时间、翻页失败率、阅读位置恢复率 |
| OCR 覆盖 | 已处理文件比例、完成书目比例、失败重试成功率 |
| 发布质量 | 构建可复现率、版本清单完整性、回归测试通过率 |

## 八、最终结论

方志检索项目已经具备较完整的桌面产品基础，其核心价值不是“访问一个网盘分享”，而是把杂乱的地方志文件整理成可检索、可定位、可下载、可阅读的书目体系。

当前最合理的策略不是继续横向增加功能，而是优先提升现有链路的可信度和连续性。完成 P0 修复后，再逐步强化 OCR、全文检索和书目治理能力，产品风险更低，也更容易形成清晰的差异化价值。
